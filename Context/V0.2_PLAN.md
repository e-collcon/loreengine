# LoreEngine v0.2 — the stable release plan

Written 21 Nov 2026 (Claudia), after chunks 1–9 and the N6 elevation rework, while E runs the v0.1 QA. Read `PROGRESS.md` first; this file says what comes between v0.1 and Phase 6.

## What v0.2 is

**v0.2 is v0.1 made dependable.** It has the same features as v0.1, with these additions:
- every failure from E's QA fixed;
- an interim LoreEngine look (D201–D204); the full UI redesign is v0.3 (V4);
- the few editor gaps that stop someone building a whole game without code;
- **Civ-style terrain** (D205, added 24 Nov): world-tiled ground textures blended across hex borders, cliff textures, decoration;
- the release plumbing (CI, versioning, a changelog).

**In one line** (E asked, 25 Nov): v0.2 is the cleanly shipped v0.1, the same engine with its QA failures fixed, plus what a demo game needs: Civ-style terrain, the editor gaps, and the release plumbing.

Its acceptance test is **the first demo game**, built entirely in the editor with Lexie's art, played from start to finish, and exported.

**Not in v0.2:** Phase 6 and later. Stats, items, skills, dialogue, quests and the rest start in v0.3 with Phase 6 (`PHASE6_DESIGN.md` v6). The Phase 16 design doc is written in parallel as documentation only; nothing from it is built in v0.2.

## Workstreams, in order

Each workstream is sized in Claudia-Code chunks, the same unit as the foundation build. "Blocks release" marks what must be done before v0.2 ships.

### W1 — QA intake and fixes (blocks release)

1. When E says QA is done, Claudia reads the results from the QA tracker (https://claude.ai/artifact/5myArj1Ln5ycQgjKDVPbgz) and files each failure in `QA_RESULTS.md` with a severity:
   - **P0:** stops playing or authoring Emberfall.
   - **P1:** wrong, but there is a workaround.
   - **P2:** polish.
2. Fix every P0 and P1, each with a regression test where the failure can be automated. Re-run the affected checks with E.
3. Rule on K1–K5. A Fail there turns into a W4 item.
4. Size: one to two chunks, depending on what QA finds.

### W2 — The interim LoreEngine UI (done; the redesign is v0.3)

- **Done in this branch (D201–D204):**
  - The editor wears the LoreEngine Design System v2: dark graphite, glass panes floating over a full-window canvas, Plus Jakarta Sans and Departure Mono, the Tosca-to-purple action gradient on Play.
  - The HUD has a matching placeholder skin, without blur, because a blur over a canvas that redraws every frame costs frame time (D203).
  - Class names and markup are unchanged, so every test and browser check still applies.
- **Moved to v0.3 (V4):** the follow-ups planned here (icons and a vertical tool rail, inspector rows, a design review), since E will purge this UI and redesign it.
- **Size:** nothing left in v0.2.

### W3 — Editor gaps that stop a full game (blocks release)

The demo game in W6 cannot be built without these:
- **Map creation and resizing (D175).** v0.1 can only edit maps that already exist.
- **Project import and export buttons.** `storage` already has `exportProjectFile` and `importProjectFile`; only the UI is missing. This is also how a game leaves E's browser.
- **A "used by" index for delete messages (D190).** Refusals should name what still uses the thing.
- **Code splitting for the 900 KB editor bundle (K5).** Lazy-load the database editors and the asset panel.
- **Size:** one chunk.

### W4 — Engine simplifications E judges in QA

Only the ones E fails under K1–K4 are done in v0.2:
- **D151:** mask the occlusion silhouette to the covered part.
- **D152:** draw outline flashes as outlines.
- **D150:** keep telegraphs from tinting units that stand in front of them.
- **K4:** wide sprites clipped at the feet.

Always done, whatever QA says:
- **V2 (E: yes):** in A\*, a step across a one-level slope costs twice the same step on flat ground, as in Catlike's Hex Map. Update D199's note and the pathing tests.

Size: up to one chunk.

### W5 — The art contract for the demo game (before Lexie delivers)

**Written 24 Nov: `ART_CONTRACT.md`.** It tells an artist exactly what the engine accepts, so Lexie's art imports on the first try:
- **Terrain (new with D205):**
  - ground textures: square, seamless, top-down, 1024 px, covering 4 × 4 world units;
  - cliff textures: seamless, face-on, 2 × 2 units;
  - decoration sprites with a contact shadow and an anchor at the base;
  - the Dordogne demo set: 10 grounds, 2 cliffs, 7 decoration sets;
  - a proof batch to send first, with grassland in both painted and vector style so E can choose.
- **Characters and props, as planned:**
  - one SVG per frame, named by its path;
  - the anchor on `id="anchor"`, otherwise bottom center;
  - figures facing right in a 96 × 128 box with the feet at (48, 118);
  - 1, 4, 6 or 8 directions, mirrored;
  - the state clips;
  - 1× and 2× atlases.
- **Gone:** "hex tops in a 112 × 64 box." The per-hex mode still works, but the demo does not use it. That box was stale anyway: since the 55° camera it renders 1.64 times too tall (D207).
- **SVG features:** which are proven, which are expected but untested, which are not allowed.

**Left to do:** import one real character, the terrain proof batch and one prop through the asset panel, and fix what breaks. Size: half a chunk, after W8.

### W8 — Civ-style terrain (blocks release; D205)

E implements `FOUNDATION_DESIGN.md` 6.6a (E, 24 Nov: "I'll implement a patch"). In order:
1. **Schema 3.1:**
   - `SurfaceTexture`, `DecorDef`, `TerrainDef.ground`, `cliffTexture` and `decor`, with `top` optional;
   - `settings.terrainBlend`;
   - an entry in `readers.ts` for each new leaf;
   - a schema 3.0 project still validates.
2. **Texture assets:**
   - upload checks (square, 512 or 1024; SVG rasterized to 1024);
   - mipmaps with repeat wrap;
   - the average color stored as the default `mapColor`.
3. **The terrain shader:**
   - world-space sampling;
   - per-vertex terrain triples and weights on the D197 mesh;
   - noise fraying;
   - cliff faces in face space;
   - the per-hex mode kept for `top`-only terrains;
   - one draw call per row strip.
4. **Decoration:**
   - the deterministic scatter;
   - kept clear of placements;
   - row-strip depth order and culling;
   - a player setting to turn it off.
5. **The hex grid overlay:** off in the player with a setting, on in the editor.
6. **Editor, Terrains database:**
   - ground and cliff texture pickers with a 3 × 3 tiled preview;
   - `repeat` and scroll;
   - the decoration list and density;
   - a lint warning when a map mixes ground and per-hex terrains.
7. **Emberfall:** the fixture gets ground textures, so the browser checks and the render bench cover the new path.
   - From Lexie's batch 1 (`packages/fixtures/art/dordogne/batch1`, arrived 25 Nov): grassland, meadow, woods floor, the limestone cliff and four decoration pieces.
   - Engine placeholders fill the terrains batch 1 does not cover.
8. **Tests and budget:**
   - the signature tests in 6.6a;
   - the render bench in ground mode (eight textures, decoration at 3 per hex) under 8 ms on E's machine.

**Size:** two Claudia-Code chunks: 1–3 in the first, 4–8 in the second. Rivers and roads along edges are not in v0.2.

**Done when:**
- Emberfall and the elevation fixture render with blended ground and no visible hex outline when the grid is off;
- a v0.1 project renders exactly as before;
- the bench holds.

### W6 — The first demo game (the acceptance test)

1. Agree the demo's scope with E and Lexie: one or two maps, three to five archetypes, one boss, a few triggers, music and sound.
2. Build it **in the editor only**: no code, no hand-edited JSON. Every point where the editor is not enough becomes a W3 item or a v0.3 note.
3. It plays from start to victory and to defeat.
4. It exports to a project file, and that file opens and plays on a second machine or a fresh browser.

Size: one chunk of authoring, plus whatever it surfaces.

### W7 — Release engineering (blocks release)

- **GitHub Actions:**
  - Typecheck, build, nondeterminism lint, tests and headless browser checks on every pull request and on `main`.
  - The GPU render bench stays manual, on E's machine.
  - Budget about 30 minutes for the browser checks on a cloud runner: the standalone player's 50 start/stop cycles alone take about 24 minutes under software rendering (measured 21 Nov; `main` is equally slow). Running fewer cycles on pull requests and all 50 on `main` would shorten the wait, but that changes a gate, so it needs E's approval.
- **Version 0.2.0** across the root and all ten packages.
- **A `CHANGELOG.md`** that starts at v0.1.0 (chunks 1–9 and N6) and v0.2.0.
- **Save compatibility:**
  - Schema 3 is frozen for v0.2.
  - A test that an autosave written by v0.1 opens in v0.2 (QA check F1, automated).
- **The playtest heap gate's thin margin** (+4.8% against 5%):
  - Switch it to counting retained objects from a heap snapshot, as `PROGRESS.md` proposes.
  - This changes a gate, so it needs E's approval.
- **The tick bench on E's machine** (`npm run bench`). Only the render bench has been run there so far.
- **Protect `main` (V5):** once the workflow runs, every change to `main` goes through a pull request whose checks pass, for E and for every Claudia. Nobody pushes straight to `main` after that.
- **The release itself:** tag `v0.2.0` and write the release notes.

Size: half a chunk. CI can start now, in parallel with QA.

## Exit criteria — v0.2 ships when

1. Every P0 and P1 QA failure is fixed and re-checked by E.
2. The terrain is Civ-style (W8): blended ground, cliff textures and decoration, within the render budget.
3. `npm run gates` is green in CI on `main`.
4. The demo game, built in the editor alone, plays to victory and to defeat, exports, and plays again from the exported file.
5. A v0.1 autosave opens in v0.2.
6. Every package is at 0.2.0, `CHANGELOG.md` is written, and `v0.2.0` is tagged.

**Estimate:** about six to seven and a half chunks (two of them W8, E's terrain patch), plus whatever QA finds.
